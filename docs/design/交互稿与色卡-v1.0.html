01

设计推导：从第一性原理出发

投屏工具的本质只有一句话：让大屏出现我手机上的画面，并且我随时能让它停下。界面的每个元素都必须服务于这句话，否则就是噪音。

行业惯例（隐性假设）底层事实推导出的设计
首页是功能宫格、推荐位用户打开 App 只为一件事；选项越多决策越慢（Hick：T ∝ log₂(n+1)）首页即设备列表，唯一主操作 = 点设备。可信设备 3 次点击完成投屏
搜不到设备 = 一直转圈组播失败是网络拓扑问题，等待不会自愈；用户分不清“还在找”和“找不到”T+3s 给替代路径（扫码 / 投屏码），T+10s 给网络诊断；每个状态都有出口
安全 = 每次都弹确认威胁来自“陌生 + 不在场”；对熟悉设备反复确认只会训练出习惯性点击首次 PIN 证明在场，之后可信设备免确认；TV 确认弹窗默认焦点在“拒绝”
品牌色越鲜艳越好投屏期间注意力在内容上，UI 只是过渡；大屏高彩度 UI 会与内容争夺注意并造成眩光低彩度单一主色相 + 中性灰阶；语义色只在状态变化时出现
延迟、码率是工程信息，不给用户看“卡不卡”是主观感受，没有数字就无法判断该怪网络还是怪设备，也不知道该调什么状态胶囊显示 ms 数值 + 色阶 + 文字等级（三重编码，色弱可用）

不可违背的基础约束

  • 认知：工作记忆约 4±1 个组块 → 每屏 1 个主操作、≤2 个次操作。
  • 设备：手机 360 dp 宽、触控目标 ≥48 dp；TV 960×540 dp、观看距离约 3 m、只有方向键 / 确定 / 返回 / 菜单。
  • 业务：北极星 = 60 秒内首次投屏成功率 ≥90%；最大流失点是“搜不到”。
  • 平台：Android 14+ 每次会话重新授权录屏；不申请定位 → 不能显示 Wi‑Fi 名称；不申请悬浮窗。

投屏中，界面在任何时刻必须回答 4 个问题

  • 连着谁？ 设备名 + 协议 + 加密状态
  • 连得好吗？ 延迟 ms + 色阶等级 + 码率
  • 出问题怎么办？ 原因 + 系统已经在做什么 + 用户能做什么
  • 怎么停？ App 内 / 通知 / 快捷图块，三处同一个动作

四条品牌形容词落地为可检查的规则：安静 = 单主色相、无渐变装饰；可信 = 承诺写可验证的事实；克制 = 语义色只表达状态；专业 = 数字用等宽数字并带单位。

02

品牌主色与 Material 3 色彩角色

主色 + 两个辅助色相 + 中性灰。表面色带极轻的主色倾向（蓝灰），让整个界面有统一的“温度”而不显得廉价纯灰。

BRAND PRIMARY · 港湾蓝 HARBOR BLUE
#2F5A82
HSL 209° · 47% · 35%　深色模式 #A2C9F0

为什么是这个颜色

  • 可信：蓝色相是跨文化研究中与“可靠、安全”关联最稳定的色相，也是系统级工具（设置、网络）惯用色相，用户不需要重新学习它的含义。
  • 安静：饱和度压到 47%、明度 35%，去掉“营销蓝”的亮度刺激；与乐播类产品常见的高饱和红 / 橙形成气质上的反差。冷色在视觉上“后退”，不抢投屏内容的注意力。
  • 科技：色相落在 209°（偏青的蓝），带一点“信号 / 通讯”的联想，又避开 230°+ 的紫蓝与霓虹感。
  • 省色值：在白底上对比度约 7.2:1（AAA），同一个颜色既能做按钮底色也能直接做文字链接，减少需要维护的 Token 数量。
  • TV 深色：深色模式取同色相高明度 #A2C9F0，在大面积深底上只承担焦点光环与强调，避免大屏眩光。

完整色彩角色 每个色块：上方为角色名（用其 on- 色书写），下方为 HEX 与该组合的实测对比度

浅色 Light手机 / 平板默认跟随系统
深色 DarkTV 接收端固定使用

03
语义色与延迟色阶
M3 只内置 error，成功与警告以 Extended Colors 四件套补齐。“信息”不新增色相，直接复用 primary 系 —— 色相总数越少，每个颜色携带的含义越确定（信息熵更低）。


  


  
延迟色阶 阈值来自 PRD 1.3：100 ms = 游戏模式目标 / Nielsen 0.1 s 阈值；150 ms = 中位数目标；250 ms = P95 上限

  

  

  
颜色永远不单独表达含义（WCAG 1.4.1）：胶囊同时显示数值、色点与等级文字。“良好”选橄榄绿而非第二种蓝，使四级在色相上单调过渡（绿 → 黄绿 → 琥珀 → 红），即使红绿色弱也能靠明度与文字区分。


  
状态胶囊组件 发送端投屏页 / 通知副标题共用；高 32 dp，内边距 12 dp，分段以 1 dp outlineVariant 分隔

对比度校验
按 WCAG 2.x 相对亮度公式在页面加载时逐对计算（非估算）。阈值：正文 ≥4.5:1（AA）、≥7:1（AAA）；大字（≥18.66 px 粗体 / 24 px）与图形边界 ≥3:1。分隔线属装饰性元素，不在要求之列。

05
字体层级
不打包字体：系统字体在 Android 上即 Roboto + Noto Sans CJK，零体积、跟随系统字号放大（≤200%，PRD 9.4），也符合 F‑Droid 的精简诉求。数字一律开启等宽数字（fontFeatureSettings = "tnum"），延迟跳动时不抖动。


  

    
TV 字号如何推导（视角等效）

    
手机：1 dp ≈ 0.16 mm，阅读距离约 30 cm → 视角 ≈ 0.00053 rad。55 英寸电视：960 dp 铺满约 1.21 m 宽，1 dp ≈ 1.26 mm，观看距离约 3 m → 视角 ≈ 0.00042 rad。TV 上同样的 dp 看起来只有手机的 0.79 倍，因此 TV 字号 ≈ 手机 × 1.27：手机正文 14 sp → TV 18 sp；手机标题 16 → TV 20~22。TV 最小字号 14 sp（仅用于辅助标签）。

参数按钮 / Chip卡片 / 大图块理由

    
      
缩放1.081.05人眼感知的是边缘的绝对位移：小元素需要更大比例；相邻间距须 ≥ (scale−1) × 尺寸，避免放大后重叠

      
填充onSurface #E1E2E8 底 + inverseOnSurface #2E3135 字深底上亮度反转是最强的前注意特征；焦点 / 非焦点底色对比约 12:1

      
外环3 dp surface 间隙 + 2 dp primary #A2C9F0 环当元素本身是浅色（如二维码卡）时，反相失效，靠外环兜底

      
光晕0 0 32 dp 6 dp，primary @ 32%增大焦点的视觉面积，余光可捕捉；按下时移除光晕作为“已确认”反馈

      
动效150 ms，cubic-bezier(.05,.7,.1,1)（M3 emphasized-decelerate）<200 ms 感知为即时；减速曲线让焦点“落定”，系统“减少动画”开启时直接切换

      
初始焦点每个页面必须声明默认焦点；返回时恢复上次焦点避免“按了方向键没反应”的失控感；敏感操作（允许投屏）不放默认焦点

图标风格
线性、圆角端点、1.75 描边（≈ Material Symbols Rounded weight 400），手机 24 dp / TV 32 dp。建议直接使用 Material Symbols Rounded（Apache‑2.0，与 GPL‑3.0 兼容）。以下为本稿使用的图标与语义。

  

  

    
规则
    
      
  • 状态图标必须配文字（图标是识别加速器，不是信息本身）。
    • 
      
  • “可信 / 加密”统一用 tertiary 色的盾牌与锁，与“连接成功”的绿色分离，避免把“已信任”误读为“已连接”。
    • 
      
  • 协议区分用文字标签 WSC DLNA + 不同图标（屏幕箭头 / 播放三角），不依赖颜色。
    • 
    

    
合规红线
    
      
  • 禁止出现苹果标志、AirPlay 三角形图标及“AirPlay”字样；统一使用通用“多设备”图标，文案写“兼容 Apple 设备（非官方）”。
    • 
      
  • 不使用 Google Cast 图标表示投屏（避免暗示 Cast 协议）。
    • 
      
  • 品牌标志（占位）：一大一小两块屏幕的叠放，小屏实心 = 发送端，大屏线框 = 接收端。

规则
  • 先排除“故障”归因（“不是连接故障”），再给替代路径 —— 用户最怕的是不知道该怪谁。

需要产品确认的问题
以下为本稿基于假设给出方案、但需要产品负责人拍板的点。每条附带本稿的默认做法。

  

    
    
      
  1. Q1 悬浮状态胶囊与“不申请悬浮窗”冲突。PRD 6.1 要求悬浮胶囊，8.5 明确不申请悬浮窗。本稿：胶囊放在 App 内 + 通知副标题实时显示延迟 / 码率，快捷图块副标题显示“投屏中”。
    2. 
      
  2. Q2 TV“允许”与 PIN 是否重复。本稿：WSC 路径需“TV 允许 + 手机 PIN”双条件；也可简化为“手机输对 PIN 即视为同意”，TV 只保留“拒绝”。后者少一步但少一道同意。
    3. 
      
  3. Q3 受保护内容如何检测。FLAG_SECURE 内容在发送端采集为黑帧，系统不通知；黑帧推断可能把真正的黑场视频误判。建议技术评审确定阈值，否则文案改为“画面可能受保护”。
    4. 
      
  4. Q4 MVP 发送端列表是否显示 DLNA 设备。DMC 推送在 V1。本稿：显示但置灰并说明“下个版本开放”，便于验证需求；也可完全隐藏以减少噪音。
    5. 
      
  5. Q5 “游戏”档位是否进 MVP。8.6 列出 4 档，但 F18 游戏模式在 V1。本稿：分段按钮保留 4 档，MVP 阶段“游戏”可先映射为 720p60 不做抖动缓冲专项优化。
    6. 
      
  6. Q6 【已决策，PRD v1.1 #19】投屏码改为 8 位（3 位 IP + 5 位 PIN），免二次 PIN。原问题：本稿：投屏码等同扫码，免二次 PIN；但 3 位 PIN 仅 1000 种组合，需配合 TV 端限次（建议 5 次错误后刷新投屏码）。另：IP 末段 <100 时投屏码是否补零（如 023）。
    7. 
    

    
    
      
  1. Q7 兼容 Apple 设备的 PIN 默认开还是关。本稿默认开（安全默认值，对应酒店误投痛点 L13），代价是 iPhone 每次连接需输入。
    2. 
      
  2. Q8 PIN 错误次数上限与锁定策略。建议 3 次错误后 TV 自动拒绝该请求，同一设备 60 s 内不可再次发起。

    5. 
      
  5. Q11 重连失败后“重新连接”是否跳过说明卡。本稿跳过，直达系统授权（用户刚经历过完整流程）。
