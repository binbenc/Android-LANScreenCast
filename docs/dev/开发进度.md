## 3. 与文档的差异与取舍（需要评审知悉）

1. **模块划分**：用户任务描述写 `:core:signaling`（纯 Kotlin，消息 + 状态机）与 `:core:security`（含 SPAKE2）；实现按技术方案 3.10.1 把纯逻辑（消息、状态机、SPAKE2、投屏码、二维码、画质）放在 JVM 模块 `:core:protocol`，`:core:signaling` 只做 WSS I/O，`:core:security` 做证书 / TLS / 可信设备 / 配对会话。新增了技术方案建议的 `build-logic`、`:core:common`、`:core:net`、`:core:data`、`:core:ui`、`:feature:settings`、`:protocol:airplay-api`，以及仓库根 `protocol/`（PROTOCOL.md + 测试向量）。
2. **内录声音实现**：技术方案的 M0 过渡方案 B（LiveKit 覆写缓冲）会打开麦克风。检查 webrtc-sdk 150.7871.04 字节码后发现它的 `WebRtcAudioRecord` 支持 `setUseAudioRecord(false)`：关闭后不创建麦克风 AudioRecord，采集线程只从 `AudioBufferCallback` 取数据。于是用它注入 AudioPlaybackCapture，**不需要 `FOREGROUND_SERVICE_MICROPHONE`、不打开麦克风**，符合 PRD S-03。代码中保留 `TODO(M1 自建 fork P1 补丁)`。是否出现麦克风隐私指示灯待真机验证。
3. **ABI 拆包 + universal 包**：技术方案写 `isUniversalApk = false`；但 F26 分发的是“手机上装的那个 APK”，只含 arm64 的包装不到 32 位电视上。因此额外输出 universal 包（`app-universal-*.apk`），F26 页面检测到只含 arm64 时给出提示。发布策略需产品决定（见第 6 节 Q-A）。
4. **AirPlay 构建开关默认值**：已按 PRD 决策 #3 改为**默认包含**（`gradle.properties` 中 `wsc.airplay=true`）；不带 AirPlay 构建用 `-Pwsc.airplay=false`。
5. **投屏码路径不再弹 TV“允许”**：按决策 #19“输对即视为完成配对”；但已有会话（镜像或 DLNA）时仍弹“请求替换当前投屏”（R-09）。PIN 路径仍是“TV 允许 + 手机 PIN”双条件（交互稿 Q2 默认做法）。
6. **SPAKE2 指纹绑定**：技术方案写“MAC 输入 = TT‖fpA‖fpB‖sessionId”；实现把 `fpA‖fpB‖sessionId` 作为 RFC 9382 第 4 节的 AAD 参与确认密钥派生，效果等价（中间人 → 确认 MAC 失败，有单测），且能直接复用 RFC 测试向量。
7. **新增 WAKE_LOCK 权限**：PRD 8.5 权限清单未列。镜像期间要保持亮屏（决策 #17），而被镜像的是其他 App，不能依赖本 Activity 的 `FLAG_KEEP_SCREEN_ON`，所以前台服务持有 `SCREEN_BRIGHT_WAKE_LOCK`（普通权限，安装时授予）。
8. **端到端延迟是估算值**：按技术方案 3.4 方法 M3 分段相加（采集 + 编码 + RTT/2 + 抖动缓冲 + 解码 + 渲染），界面标注“估算”。真值需 M1/M2 方法校准。
9. **受保护内容**：发送端每秒抽 1 帧（缩到 64×36）连续 3 秒全黑判定“可能受保护”，TV 文案改为“该内容**可能**受版权保护”（交互稿 Q3 / PRD Q12 未定，取保守文案）。
10. **重连中画面**：交互稿要求“降饱和 + 降亮度到 50%”，SurfaceView 上无法用 Compose 做降饱和，只实现 50% 压暗。
11. **游戏档**：~~中途切到 / 切出游戏档不会重新协商音视频的 stream 分组~~ F18 已解决：切进 / 切出游戏档重建媒体连接，音频分组、接收端缓冲、解码器随之生效（4.12 节）。
12. **DLNA 自动播放**：规范上 SetAVTransportURI 后应等 Play，但不少国内 App 不发 Play，实现为准备好后自动播放、收到 Pause 再暂停。
13. **开机自启**：Android 15 禁止从 BOOT_COMPLETED 启动 mediaPlayback 前台服务，只在开机时启动发现监听；没有前台服务时进程可能很快被回收，效果待真机验证。
14. **依赖版本**：除技术方案已定的版本外，`待验证` 项取当前能从 Maven Central / Google Maven 解析的版本：coroutines 1.10.2、serialization 1.9.0、BouncyCastle 1.83、ZXing 3.5.4、CameraX 1.5.3、DataStore 1.1.7、Turbine 1.2.1、navigation-compose 2.9.8、lifecycle 2.9.4、material-icons-extended 1.7.8。未引入 MockK / Robolectric（JDK 25 测试 JVM 兼容性风险，全部用假实现单测）。Hilt 2.60.1 + KSP 2.3.12 已在 AGP 9.4.1 内置 Kotlin 2.2.10 下跑通。
15. **未引入 licensee 许可证门禁**：技术方案的 deps-audit 属于 CI（未在 MVP 范围内实现 CI 工作流）。当前依赖全部为 Apache-2.0 / MIT / BSD / Bouncy Castle（MIT 风格）；`-Pwsc.airplay=true` 时另含 UxPlay（GPL-3.0）、libplist / FFmpeg（LGPL-2.1+）、OpenSSL 3.5（Apache-2.0），均与 GPL-3.0 兼容（`protocol-impl/airplay/src/main/cpp/third_party/README.md`）。
16. **UxPlay 固定到 master commit 而非 tag**：`05b0275c`（1.73.7 之后的开发线）。我们的 `android_dnssd.c` 依赖它新增的可插拔 dnssd 后端接口，v1.73.7 没有。技术方案写“跟随 1.73.x 稳定版”。
17. **不用 openssl-cmake、不用 Oboe**（技术方案 3.8 写了两者）：openssl-cmake 在 CMake 配置期联网下载源码，与 F-Droid 离线构建冲突，改为 OpenSSL 子模块 + 构建脚本；音频输出用 `AudioTrack`（ALAC 在原生层用 FFmpeg 解码为 PCM，AAC-LC / AAC-ELD 用 MediaCodec），原生代码全部是 C，`ANDROID_STL=none`，省掉 libc++_shared.so（每 ABI 1.3~1.8 MB）。
18. **兼容 Apple 设备的 R-09 实现**：iPhone 在已有 WSC / DLNA 会话时请求连接 → 弹“请求替换当前投屏”（在 UxPlay 的 httpd 线程上同步等待，35 秒上限）；WSC / DLNA 在 Apple 会话期间请求 → 原有确认流程，允许后断开 Apple 设备。**Apple 设备之间不支持替换**：UxPlay 以 `nohold=0` 运行，已有 iPhone 在投时第二台 iPhone 被 UxPlay 直接拒绝（409），不弹窗；`nohold=1` 会在确认前就抢占，不符合“确认后才替换”。设置为“每次都确认”时 Apple 设备每次连接也弹确认。
19. **视频网址的外网访问**：UxPlay 在本机 httpd 提供改写后的 playlist（本地 playlist 代理），ExoPlayer 播放 `http://localhost:<port>/…`，但分片仍直接从视频网站拉取 —— 与 DLNA 推送网址同属 PRD“用户推送的网址”例外。FairPlay 加密内容不支持（播放失败时提示“该内容不支持播放（可能受版权保护）”）。
20. **镜像不做音画同步**：视频解出即渲染、音频非阻塞写入 AudioTrack（满则丢），以低延迟优先；UxPlay 的 GStreamer 渲染是按 NTP 时间戳同步的。音画是否明显不同步待真机评估。H.265 暂不通告（功能位 42=0），只走 H.264。
21. **TV 端断开 Apple 设备 = 重启 UxPlay 服务**：UxPlay 没有线程安全的“踢掉当前客户端”接口，连按两次返回 / 被其他协议替换时停止并重新启动服务（mDNS 注册短暂撤销再恢复）。
22. **构建期补丁**：UxPlay `airplay_video.c` 对未知的 HLS `EXT-X-MEDIA TYPE` 调用 `exit(1)`（远端可触发的进程退出），CMake 在构建目录里替换为忽略该行，不改子模块；UxPlay 其余 `exit(1)` 仅在内存分配失败时触发，未处理。
23. **导出日志脱敏**：UxPlay 日志转入本地诊断日志前去掉 URL / IP，并把 “AirPlay” 字样替换为 “Apple-compat”；报告里的协议名导出为 `APPLE_COMPAT`（日志预览也是界面，PRD 12）。
24. **R8 范围**：`optimization.packageScope` 从 androidx/kotlin/kotlinx 扩大到默认的整个应用。项目代码无反射；BouncyCastle 只作为库调用（未注册 JCA Provider）；JNI 名字由 `jni.keep` 保留并有 `JniContractTest` 校验。

**发现并已修复的问题**

1. **发送端连接失败没有任何提示**（`SenderScreen.kt`）：`Ended` 状态下先调 `acknowledge()` 再 `showSnackbar()`，`acknowledge()` 把状态切回 Idle，`LaunchedEffect(state)` 重启并取消了正在显示的 Snackbar。“找不到设备 / 对方拒绝 / 尝试次数过多 / 证书校验失败”等提示全部一闪即逝。改为在 `rememberCoroutineScope` 中显示。修复后提示保持约 4 秒。
2. **TV 组件不响应触摸**（`TvComponents.kt`）：`androidx.tv.material3` 的 `Button` / `Surface` 只处理遥控器按键（`tvClickable` = focusable + 按键 + 语义，无指针输入）。接收端跑在平板 / 手机等触屏设备上时，“允许 / 拒绝 / 去开启 / 设置”点了都没反应（DLNA 确认弹窗只能用方向键操作）。`TvButton` / `TvCard` 补上点按手势。
3. **设置类页面底部被导航栏遮挡**：设置、可信设备、网络诊断、日志导出、投屏报告、安装帮助页只有 `TopAppBar` 处理状态栏，没有处理底部导航栏（`enableEdgeToEdge` 下最后一项被遮住）。外层加 `navigationBarsPadding()`；接收端待机页加 `systemBarsPadding()`（手机 / 平板当接收端时“设置”按钮压在状态栏上）。
4. **导出日志含 Apple 配对 PIN**：UxPlay 日志 `CLIENT MUST NOW ENTER PIN = "3738"` 原样进入本地诊断日志（可能被附到公开 issue）。`UxPlayLogRedactor` 增加 PIN 脱敏，单测覆盖。
5. **无障碍朗读重复标点**：诊断项朗读为“……路由器吗？。……”。标题已以问号结尾时不再追加句号。

**观察到但未改动**

- DLNA `Stop` 后状态为 `NO_MEDIA_PRESENT`（直接回到待机页）；UPnP 规范是 `STOPPED`，个别控制点在 Stop 后直接发 Play 会收到 701。主流 App 会重新 SetAVTransportURI，暂不改，真机测试控制点兼容性时再看（第 5 节 #9）。

## 4.6 真机问题：Mac 镜像到手机 PIN 总是“不正确”（2026-11-14）

现象：手机当接收端，Mac 选择镜像后输入 PIN 一直提示不正确。诊断：在手机上用 App 实际的 libcrypto 跑 UxPlay SRP 服务端、Python 实现 Apple SRP 客户端对照，3/3 通过，排除加密库问题；问题在我们的集成：

| 问题 | 处理 |
|---|---|
| PIN 覆盖层一闪而过：Mac 发完 PAIR-PIN-START 立即断开，`onConnectionDestroy`（最后一个连接关闭）清掉了 PIN，用户看不到正确 PIN | 连接关闭不再清 PIN；由原生层作废信号（`onDisplayPin("")`）、会话开始或 60 秒 UI 超时收起 |
| 上游 UxPlay PIN 用一次即清零为 "0000"：输错一次后 Mac 直接重试（不再发 PAIR-PIN-START），之后怎么输都错；且不经 PAIR-PIN-START 也能拿 "0000" 尝试配对 | 构建期补丁 `raop_handlers.h`（CMakeLists，不改子模块，匹配失败即终止构建）+ `bridge/wsc_pin_guard.c`：只接受 PAIR-PIN-START 签发的 PIN，120 秒过期，同一 PIN 失败 3 次作废并收起覆盖层，配对成功后作废 |
| JNI 没有 `raop_set_plist("pin", 0)`（uxplay `-pin` 会设），`use_pin=false` 时 PIN 配对后的 pair-verify 被拒 | `nativeStart` 在 requirePin 时设置 |

验证（真机 PJD110 / Android 16，Python 模拟客户端走真实 RTSP）：PIN 正常显示；输错后不重发 PIN-START 用正确 PIN 重试 → 200；连续 3 次错误后 PIN 收起、正确 PIN 也被拒（需重新发起）。覆盖层文案加上 Mac。**待用户用 Mac 实测完整镜像。**

### 4.8.2 模拟器回归修复（2026-11-15，两台 API 33 模拟器）

| 编号 | 问题 | 处理 |
|---|---|---|
| R3 | API 33 上没有声音播放时 playback capture 读取立即返回，采集线程以远超实时的速度向 libwebrtc 推帧，3 秒内 native 内存到 727 MB 后 Scudo NO MEMORY abort | **协调方已修复**（`PlaybackAudioCapture` 按墙钟节拍 realtimeStep + 单测），本轮未改动 |
| R4【阻塞】 | 静止按住超过快速点击路径（0.8 s / 1.5 s）后抬起，发送端 Compose 按钮不触发点击；同样的按住在桌面能弹出长按菜单，快速点击与上滑正常；发送端无异常日志 | 见下 |

R4 原因分析：静止按住会进入流式注入：DOWN 段（willContinue）之后，接收端每 250 ms 的保活 MOVE 和原地抬起都生成了**零长度续接段**（`continueStroke` 的路径起点 = 终点）。代码路径本身没有把抬起变成取消（正常抬起一直是 last=true / willContinue=false 的续接段，D5 的 Abort 只用于中止），长按菜单能弹出说明按下已保持住，问题出在静止期间的续接上。AOSP 的 `StrokeDescription` 把零长度路径当作“点按位置”处理，构造时接受；`MotionEventInjector` 在续接时要校验起点与上一段终点一致，零长度续接段的处理在 API 33 上表现为最终没有得到正常的 ACTION_UP（目标收到取消或整段被丢弃）。**零长度 continueStroke 在 API 33 上是否被接受无法在本机直接验证（不能用模拟器 / adb），按现象判定为不可用并彻底规避**。

修复：
- `StrokeSegmenter` 续接段**永不为零长度**：手指未移动（相对手指真实位置 < 0.5 px）时，改为在手指位置与其 1 px 邻点之间往返微动（远小于触摸 slop，不会变成拖动或滚动），时长取刷新间隔 16 ms（静止的时间指针已在真实时间里按着，不重放，抬起不再延迟最多 300 ms）；原地抬起同样是一段 1 px 的 last 段，系统发 ACTION_UP。
- 判定“是否移动”与手指真实位置（anchor）比较，避免微动本身被误判成移动。
- 正常抬起 = last=true 续接段（willContinue=false）；只有发送端发起的中止才用取消手势（D5 不变）。
- 追踪日志（不含坐标）：注入器每段 `#N dispatch down/move/up/tap/stroke/abort ok=…`（debug），每个手势结束一行 `gesture #N completed/aborted/rejected/dropped tail: dispatched / merged / dropped / sysCancelled / rejected`（info），系统取消 `#N system cancelled …`（info）；协调器记录按下被拒原因、进行中中止原因、无注入器、`injection cancelled by system -> LOCAL_TOUCH`。

### 4.9.6 顶边向上滚动无效修复（2026-11-15）

1. **⑧ 声音晚提示不触发**：没有可靠的音视频端到端时间差测法，按 PRD G / 交互稿“测不出来就不提示”，代码保留类型但永不产生。

6. **最近投屏行“游戏 · 约 82 ms”**（交互稿 G06 报告示意第二行）：报告页目前没有“最近投屏”列表，只做了单列的游戏模式延迟行。

单测新增：`GameModeTest`（提示队列、延迟 / 帧率判定）、`QualityTest`（游戏档不降级、`ReceiverTuning`、`QualitySwitchPolicy`、OFFER 字段兼容）、`RtcPureLogicTest`（处理耗时 / 排队增量、分段估算、厂商键）、`ReportSummaryTest`（游戏延迟单列）、`SenderCopyTest`（游戏文案）。

**模拟器可验证的步骤**（两台 API 33+ 模拟器互联，一台接收端；见第 7 节 AVD）：
1. 默认画质设为“游戏”（设置 → 画质档位，第一次弹 G01）→ 投屏：接收端日志 `peer #0 created, playoutDelayMax=0ms lowLatencyDecoder=true`，右上 3 秒“游戏模式”。
2. 均衡档投屏中点“游戏”：G01 → 开启 → 分段按钮转圈、其他档位不可点、胶囊“切换中 均衡 → 游戏”；电视保留最后一帧（>300 ms 才出小卡），恢复后标签 3 秒；发送端**不出现**“正在重连”，不再弹录屏授权；日志两端的停顿毫秒数。再切回“均衡”同样流程。
3. 切换中断开接收端网络 / 杀接收端：5 秒后发送端回原档位，回退出画面后出现提示位 ①，会话不结束。
4. 接收端装旧版（F18 之前的包）：选“游戏”只改 720p60，出现提示位 ⑤，不崩溃不断开。
5. 统计浮层：TV（force_tv）按菜单键 / 手机点按画面 →“延迟约 xx ms · 估算”、四段耗时、帧率、“一直显示延迟”开关 → 左上角常驻数字，重新投屏后开关复位。
6. 模拟器上解码器多为 `c2.goldfish.*` / 软件解码，统计浮层应显示“不支持低延迟”或无该项，且画面正常（回退路径）。
7. `adb shell cmd thermalservice override-status 4`（SEVERE）：游戏档降为 30 帧、提示位 ②、通知副标题、电视“已降为 30 帧”；`override-status 0` 后不自动回升，再点“游戏”恢复 60 帧。
8. 电量：`adb shell dumpsys battery set level 15; dumpsys battery unplug` 后切到游戏 → 提示位 ⑨；`dumpsys battery reset` 复原。

31. **F18 游戏模式（4.12 节）**：
